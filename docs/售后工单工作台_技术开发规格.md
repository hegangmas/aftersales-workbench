# 售后工单工作台技术开发规格

版本 1.0 · 2026-11-23 · 供售后、开发及信息部联合评审

本规格定义工作台的业务行为、逻辑数据模型、建议接口和验收条件。接口路径及字段为工作台拟订契约。智享乐装、MES、充电桩管理平台、400 和群助手的现有接口以实际联调为准，现场写入和回传均须验收后启用。

[业务流程与卡点评审](售后业务流程重构与落地评审.md) · [业务流程图](售后业务主流程.svg) · [Mermaid 源文件](售后业务主流程.mmd)

## 1. 范围和交付顺序

| 阶段 | 必须完成 | 退出条件 |
| --- | --- | --- |
| P0 真实数据小样 | 人工受理、设备核实、跨系统只读取证、排查指引、处理和回访记录、换班接续、验证和结束。允许人工关联智享乐装现场单或跳转，手工录入派修结果并保留来源 | 通过本规格 P0 用例。两班次完成同一问题。涉及三个来源的字段可对账，缺失时有降级路径 |
| P1 有限真实试用与集成 | 启用期限定于确认的项目、坐席和数据。验证现有群助手转人工、400 话单，逐步接通现场派修与回执。经授权的录音摘要供售后复核 | 书面确认渠道权限、接口及数据范围。通过幂等、回传异常与对账用例，再按项目开写 |
| P2 扩展 | 客户补传和进度查询、来电弹屏、规则辅助分配、聚类及质量复盘、更多项目。过保报价、支付和审批自动化按业务另行评审 | 验证实际使用、工作量和质量收益。明确预算、维护人、服务承诺和回退方案 |

P0 优先试点“插枪后未开始充电”，涵盖一个自有品牌型号和已授权数据。由专用网页承担操作。AI 辅助研发、输出事实摘要和草稿。系统规则、角色权限、状态变更与审批由服务端执行。

## 2. 架构与权责

首版建议用工作台前端、业务服务及关系型存储，配合三套自研系统适配器。独立系统查询可并行。附件使用受控对象存储或原系统受限引用。异步任务负责提醒及后续外部对账。部署方式和技术栈沿用信息部可维护的环境。网页与 MCP 如需复用，由同一个业务服务校验授权。

| 数据／动作 | 权威系统 | 工作台持有 |
| --- | --- | --- |
| 售后问题、接触记录、责任、验证 | 工作台试点业务库 | 问题、动作事件、来源引用与队列 |
| 现场派修、预约、工程师、完工、执行回执、结算 | 智享乐装 | 外部工单引用、业务必要快照及同步状态 |
| 安装与可核实的换桩关系 | 智享乐装或经确认的设备档案 | 来源映射、关系生效区间。冲突可标记待核实 |
| 在线与充电事实、故障、平台事件 | 充电桩管理平台 | 查询结果、事件引用、数据时效、诊断快照 |
| 出厂与厂内返修 | MES | 摘要与来源链接 |
| 话单、录音、群会话 | 获授权的原渠道 | 原编号及必要摘要，按批准范围存取 |
| SOP、处置授权、项目时效 | 发布规则的售后和技术主管 | 版本、生效区间、审批关系、案例应用记录 |

网关身份验证后，服务端按组织、项目、角色和记录范围校验。候选查询、详情、导出、附件与 AI 查询工具各自校验。普通坐席只读本项目和授权共享队列，当前责任或授权接班人可执行处理动作。技术二线录复核意见，主管认领兜底及处置升级，授权审批人在规则范围审批，服务商仅操作分配给自己的现场任务。质量看最少现场和返厂证据。运维维护配置与故障，配置操作和业务审批各有凭据及审计。

## 3. 状态机和动作

状态码用于开发，表内中文用于页面。唯一业务状态存于问题记录。负责人、等待原因、是否升级和现场任务状态另存，防止同一个问题同时出现几个互相冲突的状态。

| 当前状态 | 动作 | 目标状态 | 前置条件与写入 |
| --- | --- | --- | --- |
| 新接触／原记录缺失 | ACCEPT／LINK_CONTACT | OPEN，或已有问题原状态 | 核验来源事件与权限。坐席确认已有问题时只新增联系及关联，已关闭问题留给 REOPEN 或新建关联问题 |
| OPEN 待接手 | CLAIM | TRIAGING | 同一事务确认当前版本、操作者和值班权限，设置负责人及队列。未抢到返回当前持有人 |
| TRIAGING 排查中 | CONFIRM_DEVICE、ADD_EVIDENCE、LOG_ACTION | TRIAGING | 写身份确认、证据或已执行动作。保留版本及来源，事发设备可以未知 |
| TRIAGING／VERIFY_PENDING／FIELD_IN_PROGRESS | WAIT | WAITING 等待 | 等待原因、当前负责组、下次动作和到期时间齐全。保存可恢复阶段。现场任务仍可同步 |
| WAITING | RESUME | 先前阶段或 TRIAGING | 根据之前阶段与现场最新事实判定，更新负责人或下一步。到期只提醒，客户新来电或坐席动作触发续办 |
| OPEN／TRIAGING／WAITING／FIELD_IN_PROGRESS／VERIFY_PENDING／VERIFIED | ESCALATE、HANDOFF | 保持问题状态 | 建升级或交接任务，记录原因、接收组和到期。确认前原负责人或值班组兜底。原验证结论受到影响时，负责人用 RECHECK 回排查 |
| 有待接手任务的活动状态 | ACCEPT_HANDOFF | OPEN 转 TRIAGING，其余保持 | 接收人在授权目标组内。一个事务完成认领任务、转移问题责任、转移未完成回访和更新版本 |
| VERIFIED | RECHECK | TRIAGING | 发现新的相反证据或客户明确反馈未恢复，留原验证历史并记录本次理由 |
| TRIAGING | LINK_FIELD_ORDER／REQUEST_FIELD_ORDER | FIELD_IN_PROGRESS 现场服务 | P0 由坐席核对原系统有效编号。P1 正式派单必须满足项目授权和证据规则，外部结果未确认时保留排查状态及“提交中”标记 |
| FIELD_IN_PROGRESS／WAITING（挂起现场阶段） | FIELD_COMPLETED | VERIFY_PENDING 待验证；如仍待客户则 WAITING 并把恢复阶段置为 VERIFY_PENDING | 有可核实的有效回执。若还有阻碍恢复验证的现场任务，待完成后再转待验证 |
| FIELD_IN_PROGRESS／WAITING（挂起现场阶段） | FIELD_REJECTED／FIELD_CANCELLED | TRIAGING，或仍有有效任务时保留现场阶段 | 记录拒单／取消原因和下一步，生成通知，原问题继续跟踪 |
| TRIAGING | REQUEST_VERIFICATION | VERIFY_PENDING | 记录已执行的措施及验证计划。计划包含应见证据与验证人 |
| VERIFY_PENDING | VERIFY | VERIFIED 已验证，或 TRIAGING | “恢复”需满足该型号规则且附证据；“未恢复”回排查。无法验证使用 WAIT |
| VERIFIED 已验证 | CLOSE | CLOSED 已结束 | 结束原因 RESOLVED，授权人确认验证证据和告知记录 |
| OPEN／TRIAGING／WAITING／VERIFY_PENDING | CLOSE | CLOSED | 仅按适用规则和原因关闭，记审核和沟通／处置记录。有效现场任务、未决高风险升级或未接手的紧急任务需先处理 |
| CLOSED | REOPEN | TRIAGING | 原问题实际未恢复或误关，由获授权人说明原因，恢复当前责任和回访。此前已确认解决后发生的新故障通常新建并关联前次 |
| 任一活动状态 | NOTE／SUPERVISOR_ALERT | 原状态 | 保留事件。安全升级优先，不依赖遥测、上传、AI 或当前班次 |

CLOSE 非故障恢复原因包括 ANSWERED（一般咨询已答复）、DUPLICATE（附目标问题并完成引用转移）、OUT_OF_SCOPE（标记告知或交接）、UNRESOLVED_ADMIN_CLOSED（满足已确认的联系尝试和审批规则）。最后一项单列，统计中保留“未解决”。禁止循环并入，保留被并入编号和审计。安全处置流程上线前由专业人员审核。

单纯查进度时，可在原问题新增联系并结束本次咨询，原问题继续处于当前阶段。未知项目的临时问题只能由授权接待队列处理，核实项目后才开放相应数据。不确定事发设备时可记录客户反馈、安排回访和发起安全升级；绑定设备后再发起按设备的后台取证。

现场订单另有本地预约／执行投影：PENDING_CONFIRMATION、ACCEPTED、IN_PROGRESS、COMPLETED、REJECTED、CANCELLED、UNKNOWN。上游原始状态和映射版本始终保留；已完成和取消状态按上游权威版本判定。状态无法映射时生成核对任务，问题保持原阶段。超时、投诉、需专业资质、批量故障使用任务或标签表达，避免滥造状态。

## 4. 逻辑数据模型

ID 统一使用不带业务含义的字符串，所有外部编号按字符串传递。日期按 ISO 8601 带时区或 UTC 存储，界面在约定时区显示。可空字段同时有未知或未获取的说明。以下字段为逻辑最小集，可由实现拆表。

| 实体 | 主键与最小字段 | 约束与查询 |
| --- | --- | --- |
| Problem | problem_id、org_id、project_id／待核实标记、type、state、severity、symptom、event_time_range、device_link_id、owner_user_id／team_id、next_action、due_at、resolution_reason、parent_problem_id、version、opened_at、closed_at | 组织／项目＋状态／待办时间索引；活动单至少有负责组；等待单具备下一步和到期时间。owner 与项目权限匹配 |
| Contact | contact_id、org_id、channel、source_namespace、source_event_id、received_at、occurred_at、受控联系人引用、摘要 | 有外部事件时唯一键为组织＋来源命名空间＋事件 ID。人工入口按操作请求键防重复 |
| ContactProblemLink | contact_id、problem_id、relation、linked_by、linked_at | 支持一次通话涉及两个诉求和多次通话对应一问题。每条关联仅存一次，变更保留审计 |
| DeviceIdentity | identity_id、project_id、sn、source_device_ids、install_ref、valid_from／valid_to、verification_status、source_ref | SN 在已核验的项目和适用区间内查询，保存事发与当前设备关系。映射冲突提示人工处理 |
| Evidence | evidence_id、problem_id、kind、source、source_ref、event_at、ingested_at、queried_at、availability、summary、unit、attachment_ref、access_class、content_version | 区分后台事实、客户陈述和人工判断，固定引用版本。只存必要快照及链接，完整报文按权限跳转 |
| WorkEvent／FollowUp | event_id／task_id、problem_id、action、actor_id、actor_role、prior_state、new_state、reason、source_request_id、assigned_team／user、due_at、accepted_at、status | 事件追加写入。对未完成、逾期、未接手任务建立索引 |
| FieldOrderLink／DispatchRequest | link_id／request_id、problem_id、provider、external_no、idempotency_key、raw_state、source_version、mapped_state、source_at、sync_at、request_status、failure_reason | 以授权项目＋来源＋现场单号唯一识别外单。每次派修意图唯一；重复回执按事件键去重 |
| Verification | verification_id、problem_id、result、criteria_version、evidence_ids、observed_at、confirmed_by、note | 每次复测单独记录；恢复结论校验必需证据 |
| Approval | approval_id、problem_id、action_type、policy_version、technical_basis、evidence_ids、requester、approver、decision、decided_at | 服务端按当前项目审批规则核查。审批范围变化或关键证据变更时复核 |
| SOP／Policy | rule_id、version、project／model_scope、firmware_range、required／alternative_evidence、allowed_actions、escalation_rule、reviewed_by、effective_range、status | 已发布版本可回溯。同范围冲突阻止发布或由优先级明确处理 |
| Attachment／Audit | attachment_id、scope、storage_ref、media_type、scan_status、retention_class；audit_id、actor、resource、operation、correlation_id、time、result | 下载前重验权限和扫描状态。日志和审计按用途保留，业务正文及凭据不进入技术日志 |

逻辑事务将问题更新、动作事件、任务及待发送记录一起提交。敏感字段按公司规范处理。附件、录音、客户信息保留期及可复制范围由授权方在接入前定稿。

WAIT 创建或更新当前回访任务，旧任务保留变更记录。RESUME 完成本次回访待办，接续者仍需明确下一步。CLOSE 时把随问题结束的回访任务标记完成或取消，独立质量任务仍有自己的负责人。追加证据可在任一已授权活动阶段提交，用于排查、现场和验收。已关闭记录的后续材料通过有审计的业务动作登记。

## 5. 外部读模型及写回

### 5.1 查询适配

开发逐系统以两个经授权设备对账，其中一个含换桩历史。填写字段真实名、类型、单位、时区、权限、分页、上游频控、数据覆盖、空结果含义和缓存时效。MES 和运行平台均先查摘要，明细按需请求。接口权限差异决定返回粒度。

| 统一状态 | 含义 | 页面和续办方式 |
| --- | --- | --- |
| OK | 成功且有数据 | 显示采集、发生及最后刷新时间 |
| NO_DATA | 成功、范围有效但无匹配记录 | 显示时间范围，不推断正常 |
| NOT_SUPPORTED | 设备／型号／渠道未覆盖 | 展示缺口，转人工证据或原系统 |
| ACCESS_DENIED | 当前身份无可见权限 | 泛化状态，禁止跨项目透露资源存在 |
| UNAVAILABLE | 超时、失败或上游数据不可用 | 其它来源继续，允许重试或人工核对 |
| STALE | 展示有权查看的缓存且已超过建议时效 | 标注数据年龄，更新后再用于判断恢复 |
| UNVERIFIED | 设备关系或上游口径待核实 | 提示先核身份或联系接口负责人 |

历史安装售后初测曾出现接口成功但维修流转返回空数组，以及单一换装字段与其他证据可能不一致。本轮须重新实测。对流程空数组，应对照真实页面、请求类型、完整字符串订单号和权限。换桩以现场动作、原新 SN、审批和回执等交叉确认。工时字段和单位请系统方确认后再进入统计。数据读取试点不能代替生产权限和数据对账。

### 5.2 派单、回调和对账

P0 人工确认智享乐装现有编号并记录受理时间；现场执行和结算沿用原系统。P1 经批准后，每个派单意图使用稳定请求键，服务端保存请求内容、结果和版本。后台调用上游，收到可用外部编号再确认创建。同键、同内容重放返回原结果。同键、不同内容返回冲突。

若上游调用超时，先标为待确认并通过请求关联键或约定的来源编号查询。对方无法支持去重或查询时，暂停自动重试，交值班人员在原系统核实回写。回调由受信任系统发送，先校验签名、时间窗口、项目和事件唯一键，再入库。按上游版本或受确认时间推进投影，旧事件留审计，不覆盖新事实。必要时拉取当前详情恢复。异常记录进入可追踪待办，对账报告覆盖缺单、重单、状态不一致和长期待确认。

## 6. 建议 API 契约

路径以 /api/v1 开头。客户端展示服务端计算的 allowed_actions。所有写命令使用 Idempotency-Key。涉及已存在问题的写命令必须传 expected_version。列表参数 cursor、limit 由服务端限制，游标绑定当前过滤条件和可见范围。接收时间由服务端生成，外部发生时间经校验后保存。

| 方法和路径 | 请求要点 | 响应与状态 |
| --- | --- | --- |
| GET /device-candidates | project_id、query_type=phone 或 sn、query、event_at | 200 candidates，含遮罩、有效期、来源及待核对字段 |
| POST /intakes | 渠道、来源命名空间、事件编号或人工记录、现象、时间、项目、可选 confirmed_existing_problem_id | 201 problem_id、contact_id、version；相同请求返回已有结果 |
| GET /problems | project_id、state、owner、due_bucket、cursor、limit 筛选 | 200 items、next_cursor，返回逾期和待接手信息 |
| GET /problems/{id} | 问题编号 | 200 问题、version、allowed_actions、时间线摘要和相关记录入口 |
| POST /problems/{id}/evidence-query | expected_version、已确认设备、time_range、source_types、用途 | 200 查询结果集合或 202 查询任务。此请求先取证，不变更问题状态。保存证据通过 ADD_EVIDENCE |
| GET /evidence-queries/{query_id} | 查询任务编号 | 200 进度与分来源结果 |
| POST /problems/{id}/actions | action、expected_version、reason、payload；按动作校验 | 200 problem_id、state、version、event_id。异步正式派单建议返回 202 request_id |
| GET /dispatch-requests/{request_id} | 派单请求编号 | 200 待确认、成功、失败或待人工核对，成功附 external_no |
| POST /integrations/field-order-events | 上游事件 ID、外部单号、原状态、版本、发生时间、签名 | P1 启用。返回 202 接收待处理或 200 已收过 |
| POST /problems/{id}/assist | 当前版本、purpose、evidence_ids | 返回事实、假设、缺证、建议下一步、规则版本及人工复核标识。无权限或证据不足明确返回 |
| POST /attachments、GET /attachments/{id} | 上传并绑定项目／问题，下载前校验权限和状态 | 201 附件 ID 及扫描状态，下载使用受控访问 |

写动作 payload 校验示例：CONFIRM_DEVICE 需要 identity_id、核验方法与事发时间；WAIT 需要 wait_reason、next_action、due_at、owner_team_id 或 owner_user_id；VERIFY 需要 result、criteria_version、evidence_ids；CLOSE 需要 resolution_reason、客户告知情况或不适用理由；LINK_FIELD_ORDER 需要 provider、external_no、来源项目、核验人；ESCALATE 需要 priority、reason、receiver_team_id、due_at；REOPEN 需要误关或未恢复依据。

```http
Content-Type: application/json
Idempotency-Key: demo-wait-001

```

```json
{"problem_id":"P-demo-001","state":"WAITING","version":5,"event_id":"EV-demo-001","follow_up_id":"FU-demo-001"}
```

错误统一返回 code、message、request_id、必要的 field_errors。401 为身份问题，403／404 按资源可见口径返回，409 用于版本／重复请求体／并发占用冲突，422 用于状态或必填证据校验，429 为限流，503 为服务不可用。版本冲突展示最新信息供确认，禁止静默覆盖。外部部分失败随分来源结果返回。

一次取证可包含多个来源结果。每个来源最小返回 source、status、queried_at、observed_at（可空）、items、reason_code（可空）。异步等待应遵守返回的 query_id，页面用当时的设备和时间范围解释结果；用户切换设备后，旧请求的结果可回看，禁止混入新设备时间线。外部接入的签名算法、事件版本及重试间隔在适配器联调表中确认。幂等记录至少覆盖业务允许的重试窗口，按组织、主体、命令类型和请求键区分，同键重放须重新验权。

## 8. AI、时效和上线运行

AI 仅使用当前项目已授权、已确认设备的证据和已发布 SOP，输出 facts、hypotheses、missing_evidence、suggested_action、escalation_reason、citations。每个事实引用 evidence_id，每个 SOP 建议记录 rule_id／version。事实不足、规则不符、车型或版本不明时标记需人工。客户描述、附件和外部文本按数据解析，模型没有可直接派单、控制设备或批准换桩的权限。动作按角色和规则另行确认。上线前抽样核对引用及提示的适用条件。

SLA 由项目配置 service_calendar、timezone、channel、action_type、start_event、due_rule、pause_rule、escalation_target、policy_version。分别计算首联、下一回访、升级和客户实际历时。人工工时按实际查询、通话、记录、求助、复核与返工累计。暂停规则只作用于获批准的 SLA 指标。提醒按任务和版本送达一次，失败进入主管队列。配置未定时采用经确认的人工约定回访时间。

部署按试用环境、限定范围读真实数据和扩大试用逐步执行。密钥由受控服务端配置。三套自研系统查询设超时、大小及并发限制，按授权缓存；配置可关闭单一适配器和 AI。至少监控受理成功率、各源读取耗时／失败率、到期未接手、待确认派单、回调积压和重复单。对受影响的客户使用现有渠道接续。

信息部与业务执行人上线前确定容量、响应时间及备份恢复目标。建议小样实测时将可交互页面与慢数据独立加载，并记录首屏及数据完成的 p50／p95。备份应覆盖问题、联系、任务、权限规则和追溯记录，试用前确认恢复步骤。回退时暂停新入口、正式写回和自动分配，保留已记录问题及派单关联，恢复到原接待方法并完成人工对账。功能开关按项目生效。基础查询及人工操作应可独立运行。

## 9. 验收用例与决策门槛

首轮用 10–20 条脱敏历史案例回放，交给 2–3 名坐席验证，随后建议 1–2 周限定试用。所有适用的 P0 用例通过后再进入真实接待。错桩、越权、危险建议、回访无责任人列为阻断项，修复后复测。真实数据演示前确认工时基线、样本和观察窗口。
