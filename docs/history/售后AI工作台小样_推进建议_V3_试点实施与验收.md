# 售后 AI 工作台试点推进建议 · V3

2026 年 11 月 23 日｜供吴超及试点团队讨论

**建议先选一款能查到运行数据的自有品牌家充桩，从“插枪后没有开始充电”做起。** 由何刚和吴超带业务团队用 AI 开发。第一次演示请安排两位不同班次的同事处理同一个案例：第一位查对设备、判断缺什么信息并约好回访，第二位接到客户回复，打开原记录继续处理。让一线人员当场检验，客户要重复讲多少话、售后要切几次系统、下一步有没有依据。

与 V2 相比，这一版把四个决定落到了操作上：什么算同一个问题，哪些证据足够决定上门或换桩，遇到例外谁继续负责，以及如何测出统一查询和 AI 分别省了多少时间。以下分工、日期和验收办法均为建议，由吴超在启动会上确认。

## 一、用一个接待过程定下首页和工单边界

假设车主在服务商群里说“昨晚插上枪，今早没充上”，第二天家属又打了 400。接待人员要能依次回答四个问题。

| 接待中要回答的问题 | 页面和业务动作 | 判断是否好用的办法 |
| --- | --- | --- |
| 说的是哪台桩、哪一次异常？ | 用手机号或桩 SN 查候选，核对安装地点、当前设备与故障发生时间。来电人可与安装联系人不同。换桩记录按日期显示新旧 SN | 换过桩或一号多桩时，能找到事发时的设备。身份未确认时，只显示核对所需的最少信息 |
| 当时发生了什么？ | 以客户描述的时间为中心，展示最近成功充电、启动尝试、故障、最后通信及平台已有的共同异常。每条带来源、发生时间和接收时间 | 能说清哪一条是桩端事实、哪一条来自客户，以及哪段记录暂缺 |
| 这次应该做什么？ | 带出对应型号和版本的排查指引。AI 可整理证据，建议下一句问话。售后选择远程指导、约回访、技术复核或转现场，并记下理由 | 资深同事能根据同一组证据复核决定。涉及安全的现象可立即升级，无需等待照片齐全 |
| 下个人接手能做什么？ | 原问题记录保留客户原话、已查证据、措施、当前负责人、下次联系时间与恢复结果。新电话或群消息由坐席确认后关联 | 第二位同事知道上一次答应了客户什么，也知道这次还需要确认什么 |

**一次联系、一个问题、一张现场工单分别计数。** 同一问题可以关联多次联系，也可以经远程指导解决，现场工单数为零。同一台桩同时出现两个现象，坐席可分别建问题。已解决后再出现，记录新的发生时间并关联前次。这样既能识别重复来电，也能保留复发次数。

## 二、把三套自研系统接到具体决定上

| 来源 | 首版优先取什么 | 什么情况下用 |
| --- | --- | --- |
| 智享乐装 | 安装地点与时间、设备更换关系、历史报修和维修结果、未完成现场单及其节点。质保和延保按可核实的项目规则展示 | 识别设备、判断有无同一问题在办、回答客户“师傅安排到哪一步了” |
| 充电桩管理平台 | 最近成功充电、选定时间段的充电事件与故障、最后通信、可取得的软件版本及相关平台事件 | 接待时还原现场，排查中刷新，处理后查是否恢复。保存当时引用的记录，便于事后解释 |
| MES | 出厂型号、相关测试项目和结果、厂内返修记录。详细电压电流等按需展开 | 怀疑硬件问题、同类故障反复发生或需按批次复核时查。出厂测试合格只能说明当时的测试结果 |

由开发执行人拿同一台桩在三个原系统做对账，并额外选一台换过桩的设备。记清楚每个字段的关联键、含义、时间、授权范围和查不到时的显示方式。**“查询成功且无记录”“该型号不上报”“该项目无权取数”“接口查询失败”应能一眼区分。** 某个接口失败，其他已查到的信息继续可用，坐席可跳转原系统并记录人工核实结果。

会议方案图中的 400 属于咨询渠道。取数图要补上充电桩管理平台，并画出处理后的刷新验证。首页展示常用摘要，安装照片、原始报文及 MES 测试明细通过链接展开。图中的故障码、型号和排查步骤由技术人员逐项换成适用内容。

## 三、先用一次现场演示决定哪些功能复用

吴超可请已有群内 AI 项目的同事，用一条测试咨询演示“群里提问 → 知识库回复或转人工 → 生成记录 → 智享乐装收到什么 → 处理结果回到哪里”。逐步记下现有编号、操作人、可用字段和失败后的去向。会中已有人提出两个工单池可能重叠，这场演示能直接决定哪些代码还需要写。

建议群内助手负责其已获授权渠道的接入，工作台负责工程师的排查和跟进，智享乐装负责现场派单、执行、完工和结算。各自保存原编号，工作台维护关联。首版支持跳转和人工确认记录。后续接通写回时，用同一请求重复提交做测试，验证只建一张现场单。提交超时应先查原单结果再重试。智享乐装的“已完工”回到工作台后，由接待方按问题类型核对恢复证据。

## 四、把排障经验写成可复核的处置规则

请吴超选两位经常处理该型号的同事，各自独立回放三条旧案例，说出“看到什么就能决定下一步”“缺哪一条信息会改变决定”。两人意见不同的地方，正是周志磊等技术骨干与质量、研发需要确认的规则。每条规则写明适用型号和版本、可用替代证据、谁可执行、何时转交，并保留审核人与版本。

| 决定 | 建议的证据和处置办法 |
| --- | --- |
| 简单咨询或远程解决 | 保留客户现象、答复与结果。对“无法启动”，恢复证据可取后续成功启动记录或客户明确确认，并标明来源。查询进度类咨询可以直接答复并结束 |
| 客户暂不在场、无法上传 | 先取后台已有信息，再向客户请求最能改变判断的一项。允许售后代录说明或在授权范围内代传已有材料。记下约定的回访时间、负责人和待验证事项 |
| 转二线或安排上门 | 写明仍无法区分的原因、现场人员要查什么、需带什么资料或备件。把专业测量留给现场人员。遇到可能的电气安全风险，按已审核的安全流程优先转专业人员 |
| 换件、换桩或客户例外处理 | 技术理由、服务承诺和授权审批分别记录。AI 提示依据与缺项，由有权限的人作决定。例外记录说明谁批准、为什么以及后续如何复核 |
| 返厂与质量复盘 | 将原 SN、替换 SN、现场表现、软硬件版本、返厂测试条件及复现结果关联。“本次未复现”保留原义。对同型号、同批次、同版本的集中现象，由质量人员结合在用设备数和测试覆盖再调查 |

图里的 A/B/C 可以帮助标记证据来源。涉及费用或安全的动作，应另配审批人和条件。客户对资料的配合程度，可以通过“请求了什么、得到什么、是否改变了决定”来衡量，先从真实案例取得数据。

## 五、渠道、责任和客户承诺

- **外包 400。** 吴超向服务商索取接口说明、费用和一条授权测试通话，分别验证话单 ID、号码、坐席、录音可获取时间、转写及来电事件。让同一条测试通话对应到正确的问题记录。先用手工输入上线，按验证结果开通话后摘要或来电弹屏。外包坐席可见字段和录音访问范围按服务协议确认。
- **群聊和服务商。** 第一期允许群内照常接待，由坐席把必要摘要关联到问题。启用机器人前，在获准的群测试能否准确引用原问题、转给正确人员、将回复送回原会话。按项目明确谁负责安装排查、谁有权直接联系车主，保留服务商原本承担的初筛工作。
- **车企平台。** 逐项目登记可用接口、授权导出或人工查询方式。车企侧数据不可获取时显示范围和最后核实时间，沿用其认可的渠道办理。先选择自有平台有完整运行数据的项目验证诊断价值。
- **换班与时效。** 每个未结束问题指定到人或有明确值班负责人的组。换班时接班人员确认待办，超过约定回访时间进入主管清单。客户可收到“谁会在何时联系”的具体答复。会议提到的 5 分钟、10／15 分钟、2 小时涉及不同服务动作，由吴超核对项目承诺、服务时段和起止点后配置。
- **派单。** 试点先按现有排班人工领取，区分正在通话、等待客户和等待上门的单。主管能看到到期回访和无人认领的单后，再评估自动分配。评估人力时同时纳入仍在其他渠道处理的工作。

## 六、首轮开发与验收

以下节奏从试点启动日计算，由业务团队根据实际投入确认。信息部正在建设下一代系统，建议集中在源码和字段确认、只读接入核查、扩大试用前的部署审查三个节点参与。

| 时间 | 谁负责 | 当场交付或验证什么 |
| --- | --- | --- |
| 启动后第 1—2 个工作日 | 何刚确定开发执行人，吴超选型号、场景和试用坐席 | 演示现有 AI 工单流转。选 10—20 条脱敏案例，记下旧流程的查询路径、人工用时、最终结果。加入换桩、多号码、数据缺失和跨班次案例 |
| 第一轮开发 | 开发执行人用 AI 阅读相关源码并实现网页，系统对接人核实查询逻辑 | 在限定账号和环境下演示真实设备。先查身份与运行时间线，再加安装维修、相关生产摘要、排查建议和回访待办。查询逻辑可供网页与 MCP 共用 |
| 接入真实接待前 | 吴超组织两名坐席、技术骨干和开发执行人 | 用当时可见的数据回放，隐藏事后维修结论。测试错桩候选、接口超时、跨班交接和简单咨询。出现串桩、跨项目泄露或危险处置建议，修复并复测后再试用 |
| 随后 1—2 周 | 吴超组织 2—3 名坐席，开发执行人跟进问题 | 记录真实使用、回原系统的原因、人工修改的 AI 建议、重复联系及误派单。测试版本可回退，AI 暂不可用时仍能查询并人工接待 |
| 试用结束 | 吴超提出扩大、修订或暂缓的意见，何刚决策投入 | 提交案例数、覆盖率、净工时、质量变化、运行成本和维护人，列明下一代系统可复用的接口、案例和知识规则 |

首轮用只读账号、限定设备和时间范围；页面按角色和项目展示手机号、地址等信息。测试数据和源码送入公司授权的 AI 环境，调用凭据保存在服务端。开发执行人保管代码版本、运行说明和反馈记录；每次演示能指出用了哪个数据源、哪个规则版本。

## 七、用试点结果决定下一笔投入

建议把同类咨询分三种方式比较：现有流程、工作台统一查询、统一查询加 AI 辅助。组织不同坐席交叉使用难度相近的案例，避免让同一人反复做已经记住答案的题。先测统一查询减少了几次切换和几分钟，再看 AI 的摘要、问询或草稿扣除复核与返工后还能节省多少。

| 评审问题 | 统计口径 |
| --- | --- |
| 工作台覆盖了多少真实工作？ | 以试点系列全部相关咨询为分母，含找不到设备、拿不到数据、转回人工的案例。分别列出可定位、可取数、真正使用的比例 |
| 是否省人时？ | 按同一个问题累计各人查询、通话、记录、求助、复核和返工分钟。另记客户从报修到恢复的历时。比较相近类型及班次，给出样本数、中位数和耗时长的案例 |
| 是否解决得更好？ | 同时看约定回访是否兑现、恢复证据、同一问题重复联系、重复上门及误派单。试用前约定观察窗口，尚在观察的案例单列 |
| 节省能否兑现？ | 每月可释放小时约为“适用问题量 × 实际使用率 × 每个使用问题净省分钟 ÷ 60”。若节省量已按全部适用问题平均，则直接乘问题量。再核算接口、模型、维护成本，以及节省集中在哪些班次 |

若统一查询已明显省时，而 AI 建议仍需较多返工，可先扩大查询页，保留经过复核的记录草稿。若客户重复联系主要来自无人回访，下一轮应先补回访和交接。只有省下的时间能够覆盖高峰、减少付费外包工时或避免实际增员时，再据此调整编制。
